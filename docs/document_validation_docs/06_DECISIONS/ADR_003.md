# ADR 003 — LLM Usage: Controlled, Deterministic, Last-Resort

**Status**: Accepted
**Date**: 2026-Q1
**Deciders**: Core team

---

## Context

The system uses LLMs in three controlled contexts:

1. **Extraction fallback**: When regex and layout heuristics fail to find a schema field, an LLM is asked to extract the value.
2. **Schema generation**: When a user describes rules in natural language, an LLM generates the schema DSL.
3. **Test fixture generation**: LLM generates HTML documents from wine CSV rows for the test corpus.

The risk is that LLM usage introduces non-determinism, opaque decision-making, and hidden costs into a system that is supposed to be deterministic and auditable.

---

## Decision

**LLMs are permitted in the system under strictly defined conditions. Any LLM usage that violates these conditions is a bug.**

---

## Rules (Non-Negotiable)

### Rule 1: Temperature is always 0

All LLM calls use `temperature=0.0`. This is the only configuration that makes LLM output deterministic for a given model and prompt. Any call with `temperature > 0` is forbidden.

```python
# Enforced in OllamaLLMClient
async def complete(self, system: str, user: str, temperature: float = 0.0) -> str:
    assert temperature == 0.0, "LLM calls must use temperature=0"
    ...
```

### Rule 2: LLM never validates

The validation engine is a pure function with no LLM calls. LLM output never directly determines PASS/FAIL. LLM output becomes an `ExtractionCandidate` with `source="llm"` and `confidence ≤ 0.45`. It can be overridden by regex or layout candidates.

### Rule 3: LLM output is always structured and validated

LLM calls are given a system prompt that demands structured JSON output. The response is parsed with `loads_json_maybe_with_fence()` and validated before use. If the LLM returns invalid JSON or a structurally unexpected response, the call is silently ignored (not an error).

### Rule 4: LLM is opt-in and disabled in tests

`validation_llm_fallback_enabled` is `false` by default. Tests always run with this setting disabled. LLM-specific tests are marked `@pytest.mark.llm` and excluded from CI.

### Rule 5: Prompts are fixed and versioned

LLM prompts are not dynamically generated from user input (except schema generation, where the user's natural language is the input). Extraction prompts are constants in the codebase. Changes to prompts are tracked as breaking changes in the changelog.

### Rule 6: LLM is last resort in extraction

The extraction priority is: regex (highest) > layout > LLM (lowest). Even if the LLM finds a value, it is overridden by any regex or layout candidate for the same field. This ensures that adding LLM support does not degrade performance on documents that structured extractors handle well.

### Rule 7: Schema generation LLM output is always human-reviewed

The schema authoring flow requires a human to review and approve the LLM-generated schema before it is saved. The LLM output is a **draft only**. It is never automatically activated.

---

## Rationale

### Why allow LLMs at all?

Real-world documents are not perfectly formatted. Lab reports from different suppliers use different labels, abbreviations, and layouts. A purely deterministic extractor fails when field labels are non-standard (e.g. "EtOH" instead of "Alcohol"). LLMs excel at this task.

### Why these specific restrictions?

- **Temperature=0**: Without this, the same document produces different extraction results on different runs. This breaks the reproducibility guarantee.
- **LLM never validates**: Validation must be explainable. "The LLM said FAIL" is not an auditable explanation. "Value 18.0 exceeds maximum 15.0 (found in block b3, page 1)" is.
- **Disabled in tests**: LLM responses depend on the model version. If the model is updated, test behavior changes. Keeping LLM out of regression tests ensures test stability.
- **Human review for schema generation**: A schema defines what is "valid." Auto-activating a schema based purely on LLM output would allow incorrect rules to silently enter production.

---

## Consequences

- Ollama is the current LLM provider (self-hosted, controlled environment)
- Switching LLM providers requires updating `OllamaLLMClient` only — no other code changes
- The system can run fully without any LLM (turn off `validation_llm_fallback_enabled`)
- Missing fields that LLMs could find are acceptable in LLM-disabled mode; they produce `required` errors
